## 1. 从目标到反馈

一个典型的工具调用循环包含以下步骤：

1. Harness 将用户目标、相关规则、已有信息和工具说明组织成模型输入。
2. LLM 根据当前上下文生成回答、澄清问题或工具调用请求。
3. Harness 根据可用能力和执行策略处理请求，执行前完成必要检查。
4. 工具访问环境并返回数据、操作结果或错误。
5. Harness 把调用记录和结果接入后续上下文，再次请求模型。
6. 系统根据目标完成情况和运行限制决定继续、等待或结束。

这一流程是常见实现方式，并不要求所有 Agent 都采用完全相同的循环结构。

本地或远程描述的是部署位置，不决定组件职责。模型可以在远程服务运行，工具可以在本机执行；两者也可能运行在同一服务环境中。

## 2. 环境信息怎样成为上下文

知道“当前目录是 content/”，不等于知道里面有哪些文件；知道文件路径，也不等于读过正文。

环境中的信息只有通过用户提供、工具返回或其他明确的数据接入过程，才会成为模型可用的上下文。

如果完整文章已经在上下文中，模型可以直接分析，不必为了形式重复读取。若任务要求当前文件状态，则还需要考虑已有信息是否过期。

工具执行完成后，如果结果没有接入后续模型输入，模型无法仅凭本地函数已经运行这一事实获知结果。它可能重复请求，也可能在信息不足时生成不可靠的回答。

## 3. 用文章统计理解证据边界

目标：统计 content/ 中主要讨论 Agent 的主题文章，并列出标题。

执行前需要明确文章范围和分类标准，例如导航页是否排除，文章只是提到 Agent 是否算入。可以采用合理标准并向用户说明；影响结果的重大歧义需要澄清。

列出 5 个 Markdown 文件，只能证明发现了 5 个候选文件。读取正文后，才有证据判断哪些文件符合标准。

假设成功检查了其中 4 个文件，确认 3 篇符合条件，另一个文件无权读取。准确报告应为：

“已检查 4 个候选文件，其中 3 篇属于 Agent 主题；另有 1 个文件无法读取，因此尚不能确定最终总数。”

如果已确认候选清单完整，且每个剩余文件最多对应一篇文章，则总数在 3～4 篇之间。扫描范围不完整时，不能据此给出上限。

## 4. 用户授权与环境权限

| 层面     | 回答的问题               | 示例                           |
| -------- | ------------------------ | ------------------------------ |
| 用户授权 | 用户是否允许这项具体操作 | 允许检查文章，未必允许修改文章 |
| 环境权限 | 系统是否允许实际执行     | 用户同意写入，但目录仍是只读的 |

执行操作需要符合授权范围和环境限制。已有授权覆盖当前操作时，不需要机械地重复确认；目标文件、正文或操作范围发生重要变化时，应重新判断授权是否仍然有效。

用户确认不能自动改变文件系统或外部服务权限。遇到环境拒绝，应说明具体缺少的能力及可行的开通方式，不能把绕过限制当成替代方案。

在本知识库中，用户提出沉淀请求即授权在任务范围内直接整理文件；完成校验后展示 diff 供用户 review，修改意见也可直接落实，由用户自行提交。这是项目约定，不是所有 Agent 的通用要求。

## 5. 失败后怎样继续

| 情况               | 合理处理                                       |
| ------------------ | ---------------------------------------------- |
| 临时网络或服务错误 | 在调用可安全重复的前提下有限重试               |
| 参数错误           | 修正参数后重试，避免原样重复                   |
| 文件不存在         | 检查名称和位置，不擅自创建替代文件             |
| 权限不足           | 使用已授权的替代信息，或请求具体授权、环境权限 |
| 部分读取成功       | 保留已取得的证据，明确未检查范围               |
| 写操作超时         | 先确认是否已生效，避免重复写入或重复提交       |

错误中的“可重试”提示只是决策依据之一。尤其是写操作，超时可能意味着结果未收到，而不是操作未执行。需要结合操作状态和幂等机制判断是否重试。

## 6. 何时停止

| 状态           | 判断依据                             | 应输出什么               |
| -------------- | ------------------------------------ | ------------------------ |
| 完成           | 验收条件已有足够证据支持             | 结果、范围和必要证据     |
| 可以继续       | 存在安全、已授权且有助于目标的下一步 | 继续行动                 |
| 等待输入或授权 | 缺少用户选择、必要信息或许可         | 清楚说明缺口             |
| 受阻           | 当前没有可行的推进路径               | 部分结果、原因和恢复条件 |
| 达到运行限制   | 次数、时间或成本达到上限             | 未完成状态及已取得的结果 |

模型可以判断语义目标是否满足；Harness 也应通过代码控制预算、超时和停止策略。两者共同影响任务推进。

没有新的 Tool Call，只能说明模型这次没有请求工具。它可能正在回答、澄清或报告失败，不能据此认定目标已经成功完成。

## 7. 按需深入：Tool Call 在代码中的对应物

| 对象                 | 作用                                   |
| -------------------- | -------------------------------------- |
| 工具定义             | 让模型知道可请求哪些能力、需要哪些参数 |
| 工具注册表或路由代码 | 将工具名称映射到实际实现               |
| 调用记录             | 保存名称、参数和调用标识               |
| 工具结果             | 保存数据、状态及对应调用标识           |
| 上下文管理           | 将必要的历史和工具反馈接入后续请求     |

以 OpenAI Responses API 为例，模型输出中的 `function_call` 包含名称、JSON 编码的参数和 `call_id`；应用执行后用对应的 `function_call_output` 回传结果。具体字段属于该 API，不应当作所有协议的统一格式。参见 [Function Calling 官方指南](https://developers.openai.com/api/docs/guides/function-calling)。

这一流程可以直接调用应用中的函数，也可以由客户端通过 MCP 请求工具服务。使用工具不以 MCP 为必要前提。
