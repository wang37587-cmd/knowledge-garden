> [!abstract] 30 秒掌握
>
> - 跨项目通用原则放进全局 `AGENTS.md`，技术事实和业务风险留在具体仓库。
> - 需要多步执行、只在特定任务触发的流程做成个人或项目 Skill。
> - 测试规则要区分“运行多大范围”和“是否采用测试先行”。
> - 项目文件只写差异和例外，不复制全局规则。
> - 能由格式化器、测试或 CI 判断的规则，应优先交给自动化工具。

## 三层职责

| 层级             | 解决的问题             | 适合内容                                       | 不适合内容                           |
| ---------------- | ---------------------- | ---------------------------------------------- | ------------------------------------ |
| 全局 `AGENTS.md` | 所有项目共享的工作方式 | 修改边界、风险分级、依赖原则、完成说明         | 某个仓库的版本、命令和业务模型       |
| 项目 `AGENTS.md` | 当前仓库如何开发       | 技术栈、构建命令、模块结构、业务风险、测试入口 | 其他项目也需要重复维护的完整通用流程 |
| Skill            | 特定任务如何完成       | SQL 变更、功能开发、故障排查、提交和验证流程   | 每次任务都必须知道的简短基础规则     |

可以使用下面的判断方式：

```text
每次任务、每个项目都适用
→ 全局 AGENTS.md

只对当前仓库或模块成立
→ 项目或目录级 AGENTS.md

只在某类任务触发，并且包含多步流程
→ Skill
```

## 哪些内容适合放在全局

全局规则应稳定、简短，不依赖某个项目的实现细节。

适合放入全局的内容包括：

- 先阅读当前项目规则和相邻实现。
- 遵循已有代码风格，不进行无关重构。
- 验证范围与改动范围和风险匹配。
- 普通局部改动不默认运行整个仓库的全量测试。
- 增加生产依赖前说明理由。
- 完成后报告修改内容、验证命令、结果和未执行的检查。

示例：

```markdown
## 修改边界

- 只修改实现当前目标所需的内容。
- 遵循项目已有的命名、分层、日志和异常处理方式。
- 未经明确授权，不增加生产依赖或进行无关重构。

## 验证原则

- 验证范围与改动范围和风险等级匹配。
- 普通局部修改优先运行直接相关测试或模块检查。
- 公共 API、数据库结构、事务、并发、权限和跨模块改动需要扩大验证范围。

## 完成说明

- 说明修改内容、验证命令、结果和未运行的检查。
```

这些只是个人或团队可以采用的约定，不是 Codex 内置的默认测试策略。

## 哪些内容必须留在项目

只有当前仓库才能确认的事实，应保留在项目规则中：

- Java、Spring Boot、Maven 或 Gradle 的实际版本。
- 真实模块名称和构建命令。
- 数据库类型、迁移目录和数据兼容要求。
- 金额精度、幂等、事务、并发和权限等业务风险。
- 当前项目使用的格式化、静态检查和 CI 命令。
- 哪些改动必须运行集成测试或扩大构建范围。

项目规则可以使用以下模板：

```markdown
## 技术环境

- 从构建文件确认 Java 和框架版本。
- 使用仓库自带的 Maven Wrapper 或 Gradle Wrapper。
- 在这里记录真实的模块名称和构建命令。

## 数据库变更

- 记录当前项目真实的迁移目录和命名规则。
- 修改表结构时检查兼容性、回滚方式和历史数据影响。
- 涉及金额时检查精度、舍入和数据类型。

## 高风险区域

- 修改事务、并发、权限或跨模块协议前先说明影响。
- 高风险修改需要扩大测试和构建范围。
```

模板中的内容必须根据仓库事实填写，不能从另一个项目直接复制。

## 多个 Java 项目的推荐结构

```text
$CODEX_HOME/
└── AGENTS.md
    跨项目通用的修改、依赖和验证原则

$HOME/.agents/skills/
├── project-feature-engineer/
│   └── SKILL.md
└── sql-development/
    ├── SKILL.md
    └── references/
        ├── database.md
        ├── persistence-framework.md
        └── migration.md

java-project-a/
├── AGENTS.md
├── .agents/skills/
│   └── project-a-database-change/
│       └── SKILL.md
└── domain-module/
    └── AGENTS.md

java-project-b/
├── AGENTS.md
├── .agents/skills/
│   └── project-b-concurrency-review/
│       └── SKILL.md
└── domain-module/
    └── AGENTS.md
```

其中：

- 通用功能开发和 SQL 流程可以作为个人 Skill 跨项目复用。
- 项目 Skill 只保存当前仓库独有的操作流程。
- 模块级 `AGENTS.md` 只在进入对应目录工作时加入指令链。
- 项目根 `AGENTS.md` 可以作为任务路由入口，说明不同任务应使用哪些详细规范或 Skill。

## 测试、风格、依赖和高风险规则如何分层

| 主题       | 全局层                                         | 项目层                                     |
| ---------- | ---------------------------------------------- | ------------------------------------------ |
| 测试范围   | 验证范围与风险匹配，不默认运行全量测试         | 写明模块、测试类、集成测试和实际命令       |
| 测试先行   | 是否采用 TDD 由启用的工作流和项目规则决定      | 说明哪些行为修改必须先有失败测试           |
| 代码风格   | 遵循现有风格，不进行无关格式化                 | 指定格式化器、静态检查和参考实现           |
| 依赖       | 增加生产依赖前说明理由                         | 记录允许的技术栈和版本约束                 |
| 高风险改动 | 公共 API、数据库、事务、并发和权限需要特别说明 | 列出当前项目真正的高风险模块和扩大验证条件 |

> [!important]
> “只运行相关测试”规定的是最终验证范围；“先写失败测试”规定的是开发顺序。两者可以同时成立。

## 落地步骤

1. 盘点多个项目中反复提醒的规则。
2. 把真正相同的稳定原则写入全局 `AGENTS.md`。
3. 为每个仓库记录技术栈、模块、命令和业务风险。
4. 把 SQL、功能开发、排查等复杂流程提取为 Skill。
5. 检查多个总流程 Skill 的职责是否重叠。
6. 删除项目中对全局规则的机械复制，只保留差异和例外。
7. 在新的 Codex 任务中检查当前加载的规则和可用 Skill。
8. 使用一次小范围真实任务验证分层是否符合预期。

## 检查清单

- [ ] 全局规则不包含项目专属版本、路径和业务名词。
- [ ] 每个项目写明真实构建与测试命令。
- [ ] 高风险区域有明确的扩大验证条件。
- [ ] 通用流程只维护在一个个人 Skill 中。
- [ ] 项目 Skill 只保存该仓库独有的流程。
- [ ] 没有两个 Skill 同时负责完整的“分析—确认—计划—实现”流程。
- [ ] 格式和静态规则尽量由工具或 CI 执行。
- [ ] 新任务能够正确总结规则分层。

## 常见错误

### 全局规则过长

把 Java、SQL、测试和业务细节都放进全局文件，会让每个任务加载大量无关上下文。

### 项目知识被上移

某个项目使用的数据库版本、迁移目录或业务精度，不能写成所有项目的通用事实。

### 每个项目复制同一套规则

复制会形成多个需要同步维护的版本。项目文件应只写差异和例外。

### 重复总流程 Skill

多个 Skill 都负责需求分析、方案确认、实施计划和验证时，容易产生重复步骤或冲突。应保留一个主流程，再组合领域和验证 Skill。

### 把规则当成机器校验

能由编译器、格式化器、lint、测试或 CI 判断的内容，应优先由工具执行。规则只说明何时运行及允许哪些例外。

## 使用陌生仓库前的检查

项目 `AGENTS.md` 和 Skill 都可能影响 Agent 行为。进入陌生仓库后，可以先检查：

```bash
rg --files \
  -g 'AGENTS.md' \
  -g 'AGENTS.override.md' \
  -g '**/.agents/skills/**'
```

对于可能执行的脚本和外部操作，需要阅读实际内容，不要仅根据 Skill 名称判断是否可信。
