>
> - Workflow 主要由程序预先规定步骤与分支；Agent 让模型根据反馈选择下一步。
> - 两者可以组合：固定流程中的某一步可以交给 Agent，Agent 也可以调用完整流程。
> - 单 Agent 可以调用多个工具；多 Agent 强调任务、上下文或职责的分工，不等于多次模型调用。
> - 先用能完成任务的简单结构，只有分工收益明确时再增加协作复杂度。

## 1. 谁决定下一步

假设要根据知识库生成文章摘要。不同任务可以采用不同组织方式：

| 方式             | 下一步由谁决定                                   | 适合的任务形态                         |
| ---------------- | ------------------------------------------------ | -------------------------------------- |
| 单次模型调用     | 应用准备输入，模型生成结果                       | 已提供全文，只需一次摘要               |
| Workflow，工作流 | 预先定义的步骤与条件分支                         | 每次都读取指定文章、生成摘要、检查长度 |
| 单 Agent         | 模型根据当前信息和反馈选择行动，程序限制边界     | 先查找相关文章，再决定是否补读或澄清   |
| 多 Agent         | 多个任务单元分别处理子问题，由约定的协调机制汇总 | 不同领域资料需要独立研究与核对         |

这里按“谁控制步骤”区分 Workflow 与 Agent，不是所有产品都采用同一命名。该区分可对照 [Anthropic 对工作流与 Agent 的说明](https://www.anthropic.com/engineering/building-effective-agents)。

Workflow 不等于“完全没有智能”：分类、摘要等步骤可以调用 LLM。Agent 也不是没有规则：可用工具、权限、预算和终止条件仍由应用控制。

## 2. 为什么不是所有任务都要用 Agent

固定步骤更容易复现、检查和定位故障。若流程已经明确，让模型每次重新规划，可能增加调用次数和不确定性，却没有带来额外价值。

例如，“对给定的三篇文章各生成一句摘要”可以直接由程序循环处理；“找出知识库中互相矛盾的规则，并追查适用版本”则可能需要边读边调整方向。

一个实用组合是：程序固定“鉴权 → 获取资料 → 校验输出”的外层流程，把“需要继续寻找哪些证据”交给 Agent。灵活性只放在确实需要判断的位置。

## 3. 多 Agent 增加了什么

多 Agent 可以使用同一个底层模型，但具有不同任务、上下文或工具范围。也可以使用不同模型；模型数量并不是判定重点。

例如维护一个大型知识库时，可以分工检查“概念准确性”和“导航与重复内容”，再由一个协调者处理冲突。分工必须说明：各自负责什么、交回哪些证据、谁有最终写入权。

代价也很具体：

- 交接摘要可能遗漏限制或证据。
- 多个成员可能重复读取、相互等待或产生冲突修改。
- 并行处理可能缩短等待时间，但总调用量和成本可能增加。
- 多个模型给出同样答案，不代表答案已被独立验证。

需要独立性时，应让检查者核对原始资料和验收条件，而不只是认可前一个成员的结论。

主 Agent 委派、子 Agent 独立处理再返回结果，是多 Agent 的一种常见组织方式。任务说明、运行机制与验收方法见 [[AI 开发/Agent 工程/子 Agent 的原理与使用|子 Agent 的原理与使用]]，第一遍可先继续主线。

## 4. 用任务特征选择结构

先问四个问题：

1. 资料已经齐全，能否一次生成并校验？
2. 步骤固定，能否用程序编排？
3. 是否必须根据运行反馈改变步骤？
4. 是否存在可独立处理、值得隔离上下文的子任务？

这些问题用于减少不必要的复杂度，不是要求应用逐级升级。知识库只有几篇文章时，未必需要多 Agent；规模变大，也不意味着只能增加 Agent 数量。

Tool Calling 的请求、执行和反馈机制见 [[AI 开发/Agent 工程/Agent 如何运行与停止|Agent 如何运行与停止]]；工具接口见 [[AI 开发/Agent 工程/Tool 的接口与结果设计|Tool 的接口与结果设计]]。本文不重复这两部分实现细节。
