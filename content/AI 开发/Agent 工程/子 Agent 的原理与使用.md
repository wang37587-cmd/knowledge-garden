> [!abstract] 30 秒掌握
>
> - 子 Agent 是接受局部目标、在独立任务上下文中推进工作的 Agent；主 Agent 负责协调与整体交付。
> - 主模型提出委派请求，Harness 实际启动、调度和限制子 Agent，不是模型自行复制出另一个模型。
> - 主要收益是上下文分工、独立任务并行和专门配置；代价是交接损失、额外调用与协作冲突。
> - 上下文隔离不等于权限隔离，子 Agent 的反馈也不等于已通过最终验收。
> - 有明确目标、边界、证据和停止条件的子任务，才适合独立委派。

## 1. 子 Agent 是什么

子 Agent（Subagent）可以先理解为：**主 Agent 把一项具体工作交给另一个 Agent，让它在约定范围内自己推进，再把结果带回来。**

这里的关键是“自己推进”。主 Agent 不必提前告诉它每一步该怎么做；子 Agent 可以根据读到的信息，决定是否继续查找、调用工具或报告受阻。它不是一条只执行固定动作的指令，也不只是一个被赋予“专家”称号的角色。

### 1.1 主 Agent 和子 Agent，工作方式有什么不同

主 Agent 与子 Agent 通常都可以运行“判断 → 调用工具 → 处理反馈”的循环。区别主要是职责范围：

- 主 Agent 对用户的整体目标负责：拆分工作、协调进度、核对结果，最后向用户交付。
- 子 Agent 对分配给它的局部目标负责：在任务范围内寻找信息、作出判断，报告结果和没有完成的部分。
- 子 Agent 通常把结果交给主 Agent，而不是直接向用户交付最终答案。

例如，用户要求“检查知识库并给出整理建议”，可以这样分工：

```text
主 Agent：协调检查、核对与交付
├── 子 Agent A：检查内容重复
└── 子 Agent B：检查链接问题
```

图中的分支表示任务委派和结果回收关系，不表示子 Agent 只能执行一步，也不表示它们必然并行。

以子 Agent A 为例：它先读取两篇文章，发现定义相似，但还不能确定是否重复，于是继续读取相关章节，再判断哪些段落值得合并。这个过程中，它也在不断决定下一步，并不是主 Agent 每读一篇文章都要重新指挥它。

但即使 A 完成了重复检查，整个任务也还没有完成。主 Agent 仍要结合链接检查、目录结构和用户要求，决定最终提出哪些整理建议。

### 1.2 “主、子”是协调关系，不是能力等级

不要把子 Agent 理解为“更弱的小模型”。主、子 Agent 可以使用相同模型，也可以使用不同模型。“主”和“子”描述的是这次任务中谁委派、谁接收子任务，不是模型的聪明程度。

例如，同一个模型可以在主任务中负责统筹，在子任务中专门检查文章重复。它们使用相同的模型能力，但面对的任务说明、资料和工具范围可以不同，因此关注的问题也不同。反过来，应用也可以为复杂的子任务配置更强的模型，主 Agent 仍负责协调。

所以，**多个 Agent 不等于必须有多个不同的模型**。判断是不是子 Agent，重点看是否有被委派的任务、自己的执行过程和结果交接，而不是看模型名字。

### 1.3 子 Agent 在程序里到底是什么

子 Agent 不一定是一个独立进程，更不一定是一台独立机器。它可以只是同一应用中维护的另一组上下文、配置和执行状态。

仍以知识库检查为例，一个应用可以分别保存：

- 主任务的记录：用户要检查整个知识库，哪些检查已分派，哪些结果已收到。
- 子任务 A 的记录：负责重复检查，读过哪些文章，发现了哪些疑似重复，接下来需要确认什么。
- 子任务 B 的记录：负责链接检查，检查到哪里，还有哪些链接需要判断。

运行程序根据各自的记录，准备对应的模型输入、执行工具调用，再把反馈放回对应任务。即使这些调用都由同一个程序发出、都使用同一个模型服务，也可以形成主 Agent 与子 Agent 的协作。

这种“各自有任务记录”是逻辑上的区分，不自动意味着文件系统或权限相互隔离。它们可能看不到彼此的完整对话，却仍能读取或修改同一批文件；权限边界还要单独控制。

多 Agent 是更大的协作类别。主 Agent 统一协调子 Agent，只是其中一种组织形式，并不代表所有多 Agent 系统都具有固定的主从层级。

## 2. 从委派请求到结果回收

### 2.1 主 Agent 判断是否值得分工

主 Agent 中的 LLM 根据目标、现有信息和可用能力，判断某部分工作是否适合委派，然后生成子任务请求。应用也可以预先规定何时委派，不一定每次都让模型决定。

请求应包含具体目标，例如“检查指定文章中重复的完整解释，返回位置和依据”，而不只是“帮忙看看”。

### 2.2 Harness 实际启动子 Agent

运行程序处理请求，配置模型、任务说明、必要上下文、工具、访问范围、预算与结果返回方式。实际可用配置取决于运行环境，不是每个产品都能逐项单独设置。

这里不是“主模型在内部复制了一个自己”。更接近实际的理解是：主模型提出“请安排一个子任务检查重复内容”，Harness 收到请求后建立这个子任务的记录，准备它需要的资料，再发起相应的模型调用。**模型提出委派，程序把委派变成实际运行的任务。**

创建请求还可能因为能力不可用、并发限制或权限不足而失败。模型表达了委派意图，不等于子 Agent 已成功启动。

### 2.3 子 Agent 推进局部目标

子 Agent 在自己的上下文中运行“判断 → 调用工具 → 接收反馈”的循环，直到完成、受阻、被取消或达到限制。循环机制见 [[AI 开发/Agent 工程/Agent 如何运行与停止|Agent 如何运行与停止]]。

例如，子 Agent A 请求读取一篇候选文章，程序执行读取并返回正文；A 判断证据不足，又请求读取另一篇文章。每次工具反馈都会成为它下一次判断的依据。若读取被拒绝，它需要在授权范围内寻找替代证据，或报告缺口，而不是把没有读到的内容当作已确认事实。

执行可以是同步等待，也可以是后台运行，主 Agent 同时处理独立工作。后台运行不等于能无限继续，生命周期与取消策略仍由应用管理。

### 2.4 主 Agent 接收并验收

返回内容应包含结论、来源、检查范围、未完成项和不确定性；允许修改时，还应包含实际改动及验证结果。

主 Agent 核对证据、处理结果冲突，必要时补充任务。子 Agent 报告“完成”只是反馈，整体目标是否达成还需要验收。

例如，A 返回“两篇文章建议合并”，主 Agent 还要看它给出的段落位置和理由：究竟是大段重复解释，还是知识地图中必要的简短摘要？如果没有依据，主 Agent 可以要求补充检查，不能因为结果来自另一个 Agent 就直接采信。

有些框架把子 Agent 包装为工具：外部接口接收任务并返回结果，内部则运行另一套 Agent 流程。因此 Tool 与子 Agent 不是互斥分类。可对照 [LangChain 的子 Agent 架构与输入输出设计](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)；其中的默认状态和调用方式属于该框架，不是通用约定。

## 3. 为什么使用，以及付出什么代价

| 目的       | 可能的收益                                  | 对应代价                   |
| ---------- | ------------------------------------------- | -------------------------- |
| 上下文分工 | 主 Agent 只接收必要证据，不承载全部探索细节 | 摘要交接可能遗漏限制和来源 |
| 并行处理   | 独立任务同时推进，减少总等待时间            | 分派、等待、汇总也需要时间 |
| 专门配置   | 不同任务使用合适的工具、指令或模型          | 配置与职责边界需要维护     |
| 独立复核   | 从不同检查标准发现遗漏                      | 多个成员可能重复同一种错误 |

例如，内容检查子 Agent 可以读取大量文章，再只返回重复段落的位置和理由。主 Agent 不必接收全部阅读过程，但子 Agent 本身仍受上下文容量限制。这是在管理信息负担，不是获得无限记忆。

若两项独立检查分别需要 4 分钟和 3 分钟，串行约需 7 分钟；理想并行可接近 4 分钟再加协调开销。这只是示意，资源争用和速率限制可能让实际收益降低。

独立探索与并行协作的工程经验可参考 [Anthropic 的多 Agent 研究系统实践](https://www.anthropic.com/engineering/multi-agent-research-system)。是否适合自己的应用，需要用真实任务验证，而不是套用其他系统的收益数字。

### 3.1 更快不等于更便宜

并行可能缩短等待，但总费用取决于所有成员的模型与工具调用。重复传递背景、重复检索和反复交接都可能增加成本。

### 3.2 多数同意不等于事实正确

如果成员使用相同错误材料或前提，就可能一致地犯错。独立复核应查看原始需求、原文和验收标准，不只是认可前一个成员的结论。

### 3.3 上下文隔离不等于权限隔离

子 Agent 不知道主对话的全部内容，不代表它不能访问同一个文件目录。权限必须由工具执行端、沙箱或服务认证控制；委派不能扩大用户原本授权的范围。

## 4. 什么任务适合委派

适合的子任务通常能独立说明、执行和验收，例如分别研究不同方案、检查不同模块，或独立复核内容准确性与导航结构。

以下情况通常不值得增加子 Agent：

- 修改一句话、解释一个简单概念，委派开销大于工作量。
- 后一步必须等待前一步的具体结果，却被强行并行。
- 多个成员频繁修改同一个文件，难以划分归属。
- 必须复制几乎全部主上下文，子 Agent 才能完成很小的一步。
- 子任务目标模糊，最后还需要主 Agent 重新检查全部内容。

能用确定性程序完成的操作，优先考虑普通工具。例如检查文件链接是否存在可由脚本完成；判断失效链接应该替换成哪篇语义相关的文章，才可能需要模型或人工判断。

## 5. 怎样实际使用

### 5.1 用户怎样提出分工要求

在支持子 Agent 的助手中，可以这样描述任务：

> 检查知识库，把内容重复检查与链接问题检查分给两个只读子 Agent。主 Agent 检查目录结构并汇总结果。先不要修改文件，结论需要具体位置、依据和未检查范围。

这段示例明确了分工、操作边界和输出要求；它不保证所有产品支持相同调度方式。简单链接扫描仍可先交给脚本，不必为了使用子 Agent 而增加成员。

### 5.2 给子 Agent 的任务说明

| 要素       | 示例                                   |
| ---------- | -------------------------------------- |
| 目标与范围 | 检查指定文章中重复的完整解释           |
| 必要背景   | 知识地图负责入口，主题文章维护正文     |
| 判断标准   | 简短摘要不算重复，大段同义解释需要检查 |
| 操作限制   | 只读，不修改、不提交、不对外发送       |
| 输出要求   | 文件、章节、依据、建议和不确定项       |
| 停止条件   | 范围内检查完成；无法读取则报告具体缺口 |

传递完成工作需要的信息，而不是默认复制全部聊天历史。尤其不能省略授权范围、已确认决定和关键事实来源。子 Agent 是否继承历史、是否保留跨次状态，要按实际实现确认。

### 5.3 修改任务怎样避免冲突

可以让子 Agent A 负责模型基础文章，子 Agent B 负责状态与记忆文章，主 Agent 统一更新知识地图。这样不同成员具有清楚的写入归属。

独立工作区可以减少文件冲突，但不能自动解决内容矛盾。如果 A 修改了定义，B 仍按旧定义写作，汇总时仍需要统一概念与链接。

### 5.4 主 Agent 怎样验收

核对指定范围是否覆盖、证据是否支持结论、成员是否采用相同判断标准、操作是否越界，以及合并后的整体结果是否满足用户目标。验证方法见 [[AI 开发/可靠性/验证、评测与执行追踪|验证、评测与执行追踪]]。

## 6. 开发实现的最小心智模型

以下是表达职责的伪代码，不对应可直接运行的 SDK。示例假定 `start_subagent` 会启动后台任务，`wait_for` 等待结果；不同框架的同名或相似函数不一定具有这些语义。

```python
async def review_knowledge_base(request):
    scope = resolve_allowed_scope(request)

    job = start_subagent(
        task="检查重复解释，返回位置和依据",
        context=scope,
        tools=read_only_tools,
        budget=child_budget,
    )

    # 主流程处理不依赖子任务结果的工作
    navigation = check_navigation(scope)
    duplicates = await wait_for(job)

    verified = verify_findings(duplicates, navigation)
    return summarize(verified)
```

真正实现时，除了模型调用，还要明确：

- 创建、运行、完成、失败和取消状态如何记录。
- 超时或失败时，哪些任务可以安全重试。
- 主任务取消后，是否取消子任务及其尚未完成的工具操作。
- 是否允许继续创建下级 Agent，以及深度、并发和总预算上限。
- 结果、证据和修改记录怎样返回主 Agent。

如果允许递归委派却没有限制，系统可能不断拆分和消耗资源，却没有完成实际工作。

## 7. 与已有概念的衔接

LLM 提供判断能力，Harness 管理实际执行，Tool 承载可调用能力。Skill 可以指导怎样分工和验收，但不是一个正在运行的子 Agent；MCP 可以连接任务需要的外部能力，但创建子 Agent 不以 MCP 为前提。

这些职责的完整定义见 [[AI 开发/基础概念/AI 开发核心概念|行动与编排的核心概念]]。子 Agent 设计的核心是任务边界、信息交接和最终验收，而不是成员越多越好。
