> [!abstract] 30 秒掌握
>
> - LLM 是处理输入、生成回答的模型；Prompt 表达任务要求；Context 是本次处理时可用的信息。
> - 按上述用法，Prompt 是 Context 的一部分；不同资料也可能用 Prompt 泛指整个输入。
> - 上下文可以包含指令、对话、文章和工具结果，但不等于电脑里的全部数据或所有历史记录。
> - 回答不理想时，可以分别检查任务是否清楚、信息是否齐全，以及模型能力是否适合。
> - Token 是输入输出的计量单位；结构化输出约束结果形式，但不保证内容正确。

## 1. 三个概念怎样配合

假设用户要求：“根据这篇文章，用三句话向初学者解释 Agent。”

| 概念            | 关注的问题             | 在例子中的作用                               |
| --------------- | ---------------------- | -------------------------------------------- |
| LLM，大语言模型 | 谁处理输入并生成回答   | 理解文章、组织解释                           |
| Prompt，提示    | 希望模型做什么、怎样做 | 根据文章解释 Agent，面向初学者，限制为三句话 |
| Context，上下文 | 这次实际提供了哪些信息 | 任务要求、文章正文及被接入的相关规则和对话   |

这里用 Prompt 指任务要求，用 Context 指本次可用的整体信息，因此两者不是互斥对象。有些文档会把指令、示例和背景材料一起称为 Prompt，也有些会用 Context 专指补充材料。阅读时应先看作者采用的范围，不必强行套用唯一术语边界。

## 2. 改变哪一部分，会影响什么

- 调整 Prompt，例如指定读者和篇幅，会影响回答的重点与表达方式。
- 补充 Context，例如加入项目文章，会给回答增加具体依据。
- 更换 LLM，可能改变理解、推理和生成任务的表现。

三个因素相互影响。要求再明确，也不能保证模型准确回答缺少依据的项目事实；资料齐全，也不保证模型一定理解正确。

## 3. 什么信息算进入了上下文

用户粘贴的文章、应用接入的检索片段、工具回传的内容，都可以成为上下文。聊天界面显示的全部历史，未必每次都完整提供给模型。

只告诉模型一个文件路径，通常提供的是位置线索。模型需要通过应用提供的读取能力取得正文，或由用户直接提供正文，才能据此分析。具体反馈过程见 [[AI 开发/Agent 工程/Agent 如何运行与停止#2-环境信息怎样成为上下文|Agent 如何运行与停止]]。

上下文中的参考资料不自动成为可信事实，也不自动获得指令权限。文章内容是待分析材料，应用或用户的任务要求决定如何使用它。

模型训练中形成的能力和知识，与本次提供的上下文也应区分：补充一篇文章，让模型在这次回答中参考它，不等于已经重新训练模型或建立了长期记忆。

## 4. 回答不理想时，先看哪里

| 现象                               | 优先检查                                 |
| ---------------------------------- | ---------------------------------------- |
| 回答角度或篇幅不合适               | 任务要求是否清楚，是否说明读者与输出形式 |
| 回答很泛，缺少项目细节             | 相关资料是否真正进入上下文               |
| 回答引用了过时或错误信息           | 输入材料是否可靠、是否符合当前任务范围   |
| 有资料也有明确要求，仍频繁理解错误 | 模型能力是否适合任务，并通过实际例子验证 |

这些是检查方向，不是一一对应的故障诊断。复杂问题还可能涉及检索、工具或流程实现。

## 5. Token 与上下文窗口

Token 是模型处理内容的单位，不固定等于一个汉字或一个英文单词。分词方式、语言和内容都会影响数量，不能把字符数直接当成 Token 数。

上下文窗口限制一次请求能容纳多少内容。输入不仅包含用户问题，还可能包含规则、历史和工具结果；同时需要考虑输出空间，部分模型还计入推理 Token。具体限制应查看所用模型与接口，不把某个数字当作所有模型的共同上限。参见 [OpenAI 的上下文窗口说明](https://developers.openai.com/api/docs/guides/conversation-state#managing-the-context-window)。

窗口大不代表应该塞入全部资料。过多无关内容会增加处理负担，也可能干扰回答。哪些信息需要保留、怎样压缩，见 [[AI 开发/状态与记忆/状态、记忆与上下文管理|状态、记忆与上下文管理]]。

## 6. 从自然语言到结构化输出

给人阅读的回答可以是普通文字；交给程序处理时，通常需要稳定字段，例如文章标题、分类与判断依据。

```json
{
  "title": "Agent 如何运行与停止",
  "topic": "Agent",
  "reason": "正文主要解释执行循环与停止条件"
}
```

这是应用自定义的结果示例，不是某个 API 的固定返回格式。仅在 Prompt 中要求“输出 JSON”，与使用接口支持的 Schema 约束不是同一保障级别。后者可以约束字段、类型和允许值，但应用仍需处理拒绝、截断及业务内容错误。可对照 [Structured Outputs 官方说明](https://developers.openai.com/api/docs/guides/structured-outputs)。

“分类字段是合法字符串”和“分类真的正确”是两种检查。结构化输出方便程序读取结果，Tool Calling 则表达对工具的调用请求；具体执行见 [[AI 开发/Agent 工程/Agent 如何运行与停止|Agent 如何运行与停止]]。
