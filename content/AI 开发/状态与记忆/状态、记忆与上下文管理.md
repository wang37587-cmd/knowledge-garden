>
> - 状态描述任务进行到了哪里；记忆保存后续可能有用的信息；Context 是这次真正提供给模型的信息。
> - 会话历史只是可用材料之一，不等于每轮都会完整送入模型。
> - 短期记忆通常服务当前会话，长期记忆跨会话保留；它们通常由应用存储，不是模型自动更新参数。
> - 摘要和压缩可能丢信息，关键事实应保留来源，关键操作状态应有可靠记录。

## 1. 五种信息不要混为一谈

| 概念     | 关注什么                   | 知识库助手中的例子                   |
| -------- | -------------------------- | ------------------------------------ |
| 任务状态 | 当前进度和执行结果         | 已读哪些文件、哪些失败、草稿是否写入 |
| 会话历史 | 发生过哪些交流             | 用户问题、模型回答、工具调用记录     |
| 短期记忆 | 本次任务后续仍需使用的信息 | 当前分类标准、尚未解决的疑问         |
| 长期记忆 | 跨会话仍有价值的信息       | 用户确认的阅读偏好、稳定项目约定     |
| Context  | 本次模型实际接收的信息     | 当前问题、选取的历史、检索片段和规则 |

这些类别可能重叠，不要求各建一个数据库。例如，会话历史可以作为短期记忆的一部分，任务状态可以与执行记录一起存储。可参考 [LangChain 的记忆概念划分](https://docs.langchain.com/oss/python/concepts/memory)，但不要把某个框架的数据结构当作通用标准。

## 2. 保存了，不代表模型这次看到了

一次后续请求通常需要经历三个环节：

1. **保存**：应用记录历史、任务状态或经确认的长期信息。
2. **选取**：根据当前问题、权限和容量选出相关部分。
3. **接入**：把选出的信息组织进本次 Context。

模型本身不必一直运行。应用可以在下一次调用时重新提供必要状态；有些服务也提供会话持久化能力，底层仍需要管理后续请求使用哪些信息。参见 [OpenAI 的会话状态说明](https://developers.openai.com/api/docs/guides/conversation-state)。

比如，昨天已经保存“文章标题不带序号”，今天如果没有加载这条规则，模型就未必按它执行。反过来，曾经说过的临时要求，也不应该未经判断变成永久偏好。

## 3. 上下文太长时保留什么

上下文管理不是一味删短，而是保留能支持下一步决策的信息：

- 当前目标、适用规则和授权范围。
- 已确认的事实及来源位置。
- 已执行操作的结果、未完成项和具体错误。
- 仍需判断的分歧，而不是把猜测写成定论。

可以移除重复工具输出、筛掉无关历史，或对旧内容做摘要，需要细节时再读取原文。容量概念见 [[AI 开发/基础概念/LLM、Prompt 与 Context#5-token-与上下文窗口|Token 与上下文窗口]]。

> [!warning]
> 摘要可能省略条件。涉及“是否已付款、文件是否写入、用户是否授权”等关键状态时，应核对可靠的业务记录或操作结果，不能只凭摘要中的一句话决定行动。

## 4. 长期记忆需要更新和遗忘

记忆条目最好能够说明适用对象、来源和更新时间。例如，“这个项目不自动 commit”是项目规则，不一定适用于用户的所有仓库。

长期保存前应判断信息是否稳定、是否有必要、是否允许保存。系统还需要支持纠正、删除、过期处理和访问隔离；不能把其他用户的记忆检索进当前用户的上下文。

本知识库的正式知识维护在文档中。对话摘要是整理素材，不取代正式文章；同一结论更新时应维护其唯一正文，避免“记忆里一个版本、文档里另一个版本”。

## 5. 与 RAG 的关系

长期记忆可以通过检索选入上下文，因此能复用 RAG 中的部分技术。但两者不是同义词：产品手册是外部知识，用户偏好是记忆；任务执行到哪一步，通常更适合精确的状态记录，而不是仅靠语义搜索猜测。

第一遍先记住：**存储负责留住信息，检索或选择负责找出信息，上下文负责把信息交给模型。**
