## 1. 为什么有了模型，还需要资料

模型可以解释“什么是 Agent”，却未必知道“这个项目现在允许直接修改知识文件吗”。后一个问题取决于当前项目规则，不能只凭通用知识回答。

| 比较角度 | 模型训练中形成的知识                   | 外部资料                             |
| -------- | -------------------------------------- | ------------------------------------ |
| 存在形式 | 学习结果体现在模型参数中               | 文档、数据库记录、网页等可访问数据   |
| 典型作用 | 理解语言、解释概念、推理和生成         | 提供项目事实、当前状态和可核对来源   |
| 更新方式 | 通常需要训练或更换模型版本来更新参数   | 修改资料，并同步应用使用的索引或缓存 |
| 主要边界 | 可能过时、记忆不准确，不能保证追溯出处 | 可能错误、过时或没有被正确检索到     |

模型参数不是可以逐条查阅的原文库。外部资料也不天然正确；应用仍需选择适用版本和可靠来源。

在常见的 RAG 应用中，生成模型利用自己的能力理解检索到的资料，资料提供本次回答的具体依据。

## 2. 知识库、检索和 RAG 分别做什么

| 概念              | 负责什么                   | 知识库助手中的例子                           |
| ----------------- | -------------------------- | -------------------------------------------- |
| 知识库            | 保存和组织可用资料         | 项目的 Markdown 文章及相关规则               |
| 检索              | 根据问题查找候选资料       | 找出与“写入授权”有关的段落                   |
| RAG，检索增强生成 | 把检索到的资料用于模型生成 | 根据当前规则解释是否可以直接写入，并给出来源 |

RAG 是 Retrieval-Augmented Generation 的缩写。其核心联系是将模型生成与可检索的外部知识结合；相关研究见 [Lewis 等人的 RAG 论文](https://arxiv.org/abs/2005.11401)。

仅保存文档，还没有形成问答能力；仅返回搜索结果，也没有完成基于结果的生成。手工粘贴一篇文章可以提供上下文，但没有体现自动检索这一环节。

## 3. 一次知识库问答怎样发生

假设用户问：“这个项目的文档修改后由谁提交？”

1. 应用在用户可访问的资料范围内检索，找到当前项目规则中的相关段落。
2. 应用选取适用的内容，连同问题和来源信息提供给模型。
3. 模型根据这些材料组织回答，说明适用范围并标注依据。
4. 用户可以沿来源回到原文核对；证据不足时，回答应明确缺口。

此例中，如果检索到的当前规则是“用户 review 后自行提交”，模型就有依据回答。若检索到旧版规则，即使语言流畅，也可能给出错误结论。

资料通常需要预先整理成便于检索的形式，例如提取正文、保留来源、建立索引。每次提问时再从中选取相关内容。更新原文件后，如果索引尚未同步，问答仍可能使用旧资料。

“分块”是把长文分成可独立检索的片段；“索引”帮助快速找到它们。片段应保留标题、来源和必要上下文，避免只截取结论而丢掉适用条件。更新或删除资料时，也要同步索引中的旧片段。

## 4. Embedding 和向量数据库在哪里

检索可以使用不同方法。关键词检索寻找词语匹配；语义检索尝试找到含义相关的内容。例如，“谁负责提交”与“用户自行 commit”用词不同，但可能讨论同一问题。

Embedding 把文本等内容表示成一组数字，便于计算相似程度。向量数据库提供存储和检索这类表示的能力；原文和来源信息仍需保留或能够关联回去。相似度只是候选相关性的信号，不是真实性证明。

关键词和语义检索也可以组合使用。可对照 [OpenAI Retrieval 文档](https://developers.openai.com/api/docs/guides/retrieval) 中的语义搜索、向量存储和混合检索说明。

因此，RAG 也可以采用关键词搜索或其他检索方式，不一定需要专门的向量数据库。第一遍只需记住它们服务于“找资料”这个环节。

## 5. 与训练和 Agent 的边界

| 容易混淆的概念 | 与 RAG 的关系                                                              |
| -------------- | -------------------------------------------------------------------------- |
| 训练或微调     | 会更新模型参数；常见 RAG 应用通过提供资料影响本次回答，两者可以组合        |
| Context        | 检索结果成为上下文的一部分；上下文还可能包含指令、对话等信息               |
| Agent          | 可以根据反馈决定是否检索、继续找什么；固定的“检索后回答”流程也可以实现 RAG |
| MCP            | 可以为应用提供搜索或读取工具，但不等同于完整的 RAG 流程                    |

部分 RAG 研究和系统也会训练检索器或生成模型，因此“RAG 永远不涉及训练”并不准确。这里关注的是无需重新训练生成模型就能利用外部资料的常见应用方式。

如果任务进一步要求修改文档或执行其他操作，就从知识接入进入行动与编排，参见 [[AI 开发/Agent 工程/Agent 如何运行与停止|Agent 如何运行与停止]]。

## 6. 先检查资料，再检查回答

知识库问答至少有三个可能出错的环节：

- 资料本身不准确，或版本不适用。
- 检索遗漏关键内容，或返回了无关片段。
- 模型误解材料，或生成了材料不支持的结论。

引用来源有助于核对，但有引用不代表结论必然受原文支持。检索不到也不代表知识库一定没有答案。

对“共有多少篇相关文章”这类要求完整覆盖的任务，仅取最相关的几个搜索结果通常不够。完整统计与候选结果的区别已在 [[AI 开发/Agent 工程/Agent 如何运行与停止#3-用文章统计理解证据边界|Agent 如何运行与停止]] 中说明。
