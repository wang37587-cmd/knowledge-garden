# Quartz 知识沉淀与迁移设计

## 背景

现有个人知识库通过项目根目录的 `AGENTS.md` 约束 Codex：用户提出沉淀意图后，先展示候选知识稿，确认后再写入 Markdown。该流程解决了写入授权问题，但实际沉淀结果仍接近对话输出汇编，存在以下问题：

- 知识正文保留了过多问答过程、重复解释和临时判断。
- 不同知识类型机械套用同一组章节，主次不清。
- 单篇文档覆盖多个独立学习目标，篇幅长且难以快速复习。
- 知识内容与 Quartz 展示项目分属两个仓库，形成双重事实来源。
- 现有规则没有充分利用 Quartz 的 frontmatter、Callout、Wikilink、Backlink、图谱和搜索能力。
- 写入后主要依赖人工检查，缺少可重复执行的内容校验。

`/Users/wangwei/project/github/knowledge-garden` 已经是可运行的 Quartz v5 项目，并具有适合中文知识花园的基础样式。本次改造将它升级为学习、沉淀、维护和展示知识的统一项目。

## 目标

- 将 `knowledge-garden/content/` 设为唯一知识源。
- 后续直接在 `knowledge-garden` 项目中发起学习和沉淀任务。
- 将对话视为编辑素材，而不是需要保存的正文。
- 根据知识点和学习目标决定合并、拆分、文章类型和展示形式。
- 默认采用“先速览、再深入”的渐进式阅读结构。
- 保留完整候选稿和明确确认后写入的安全边界。
- 使用确定性脚本检查 frontmatter、链接、结构和构建结果。
- 从原任务重新提炼并迁移现有 Codex 长文，而不是复制旧稿。

## 非目标

- 不自动保存每一次对话或任务。
- 不在首次改造中批量沉淀全部历史任务。
- 不建设数据库、向量检索服务或对话同步后台。
- 不修改 Quartz 核心渲染流程。
- 不新增运行时依赖。
- 不取消人工审核和明确写入确认。
- 不把知识正文组织成时间线、聊天记录或迁移日志。

## 核心决策

### 单一事实来源

`knowledge-garden/content/` 是唯一正式知识源。旧仓库 `/Users/wangwei/Documents/ChatGPT/知识库` 在迁移完成后退役，不再保存一份可继续维护的知识副本。

迁移成功前，旧仓库中尚未提交的主题文档和 README 修改保持不变，仅作为迁移素材。迁移内容通过构建和链接校验后，旧仓库只保留指向 `knowledge-garden` 的退役说明。

### 规则、编辑能力与校验分离

采用以下结构：

```text
knowledge-garden/
├── AGENTS.md
├── .agents/
│   └── skills/
│       └── knowledge-distillation/
│           ├── SKILL.md
│           └── references/
│               ├── editorial-model.md
│               └── quartz-writing.md
├── content/
│   ├── index.md
│   └── 按主题组织的知识文档
└── scripts/
    └── validate-content.mjs
```

各部分职责如下：

- `AGENTS.md`：沉淀触发、候选稿协议、写入授权、安全边界、唯一知识源和写入后检查。
- `knowledge-distillation` Skill：知识提取、去重、主题粒度判断、文章类型选择、Quartz 表达和编辑质量检查。
- `content/`：正式知识内容和导航入口。
- `scripts/`：可以确定性执行的结构、链接、元数据和构建前检查。
- Git：保存版本历史和恢复路径，正文不维护逐条更新记录。

这种拆分避免把所有编辑细节持续堆进 `AGENTS.md`，也让知识编辑流程能够独立迭代和验证。

## 沉淀数据流

```text
学习或问题讨论
      ↓
识别沉淀意图
      ↓
确定当前任务、历史任务或文档素材范围
      ↓
读取相关已有主题
      ↓
提取知识单元并删除对话噪声
      ↓
判断补充、合并、拆分、关联或新建
      ↓
选择文章类型和 Quartz 表达形式
      ↓
展示完整候选稿
      ↓
用户确认当前候选版本
      ↓
写入 content/
      ↓
内容校验、项目检查、Quartz 构建和页面检查
```

## 知识提炼模型

### 素材范围

- 默认使用当前任务中的有效讨论。
- 用户明确提及原对话时，读取对应历史任务。
- 多个相似任务可能导致不同结果时，先请用户指定范围。
- 旧知识文档可以作为补充素材，但不能因为其已经成文就默认保留原结构。
- 原任务标题、任务 ID、问答轮次和执行状态不进入正式文章。

### 知识单元提取

Skill 从素材中识别：

- 本次学习要解决的核心认知问题。
- 已确认的定义、事实、原理和因果关系。
- 可以复用的方法、步骤和判断标准。
- 能够帮助理解的代码、配置、命令、类比或案例。
- 重要边界、适用条件、权衡和常见误区。
- 需要时效核对、存在冲突或仍不确定的内容。

以下内容默认排除：

- 用户与 AI 的逐轮问答。
- 工具调用、状态更新、计划汇报和确认提示。
- 为当前对话临时补充、但没有长期价值的上下文。
- 同一结论的多次改写。
- 没有证据支持的推断。
- 密码、令牌、私人账号和其他敏感信息。

### 主题边界

一篇文章原则上回答一个可以独立理解的核心问题。出现下列情况时应拆分：

- 内容具有独立定义、原理和使用场景。
- 该知识点经常需要被其他文章单独引用。
- 不同部分服务不同学习目标或文章类型。
- 保留在同一篇中会使速览结论失焦。

紧密相关、无法独立理解的小概念保留为同一篇文章的章节。拆分后的主题使用 Wikilink 建立语义关系，Quartz 自动生成反向链接，不要求为了形式机械互链。

## 自适应文章类型

Skill 根据主要学习目标选择文章结构，不使用统一的固定模板。一篇文章可以组合最多两种相邻类型，但必须有一个明确主类型。

| 类型       | 主要问题                       | 推荐表达                                 |
| ---------- | ------------------------------ | ---------------------------------------- |
| 概念解释   | 它是什么，与相近概念有什么区别 | 30 秒掌握、定义、心智模型、易混淆概念    |
| 原理与机制 | 它由什么组成，如何运转         | 核心结论、组成部分、流程图、边界条件     |
| 操作指南   | 什么时候用，如何正确完成       | 适用场景、前置条件、步骤、验证、异常处理 |
| 对比与选型 | 应该选择什么，代价是什么       | 推荐结论、对比表、选择条件、权衡         |
| 问题排查   | 为什么出错，如何定位和预防     | 现象、证据、根因、处理、预防             |
| 速查资料   | 如何快速找到高频信息           | 高频结论、表格、命令、配置片段           |
| 学习路径   | 应该按什么顺序理解一组主题     | 知识地图、前置知识、推荐顺序、主题入口   |

## 渐进式阅读结构

所有正式主题默认先帮助快速回忆，再允许继续深入：

```markdown
---
title: ...
description: ...
tags: [...]
aliases: [...]
---

> [!abstract] 30 秒掌握
> 最重要的 3～5 条结论。

## 根据文章类型组织的核心内容

## 示例或实践

仅在能明显帮助理解时出现。

## 易混淆概念与注意事项

仅记录真实存在的边界或误区。

## 相关知识

链接到实际存在的主题。
```

这是一套可裁剪的阅读骨架，不是必须填满的章节清单。文章不创建空章节，也不为了满足模板重复内容。

## Quartz 内容表达规则

- `title` 表达知识问题或主题，不使用“某次对话总结”“学习记录”等名称。
- `description` 用一句话说明文章帮助读者理解或解决什么。
- `tags` 数量保持少而稳定，服务分类和检索，不复制标题中的所有词。
- `aliases` 用于英文名、中文名、缩写和常见别称。
- 核心结论、提示、风险和示例可以使用 Quartz/Obsidian Callout。
- 对比信息优先使用 Markdown 表格。
- 三个以上对象的关系或多步流转才考虑 Mermaid，简单关系使用文字或列表。
- 命令、代码和配置使用标注语言的代码块。
- 只创建指向真实文件的 Wikilink 或 Markdown 链接。
- 相关知识基于语义关系建立，不为了让图谱显得密集而堆链接。
- 不直接修改 Quartz 核心样式来弥补信息架构问题；首次改造优先通过内容结构使用现有样式能力。

## 候选稿与写入授权

首次沉淀请求始终进入候选稿阶段，即使同一条请求包含“直接写入”或同义表达。

候选稿必须包含：

1. 使用的素材范围。
2. 建议新增、补充、拆分、合并、关联或删除的文件。
3. 每篇文章的主类型和归属路径。
4. 整理后的完整正文。
5. 计划新增或调整的内部链接。
6. 主动排除的对话噪声和重复内容类型。
7. 不确定、冲突或不适合沉淀的内容。

只有用户在看到当前完整候选版本后明确表示“确认写入”“按这个版本保存”等立即写入意图，才能修改 `content/`。

授权只绑定当前候选版本。候选内容、路径、拆分方式或链接关系发生任何调整后，旧授权立即失效，必须重新完整展示并获得确认。

写入时只修改已确认的知识文件和必要导航入口。校验过程中如果发现需要改变知识含义或正文，必须重新进入候选稿阶段；纯格式、链接语法或构建兼容性修复可以直接完成。

## 现有知识迁移

### 素材

首次迁移使用：

- 历史任务“配置跨项目 Codex 规则”的完整对话。
- 旧仓库未提交的 `Codex 持久化规则与扩展机制.md`。
- 旧仓库 `个人知识库/README.md` 中的索引修改。

独立任务“学习 AI 开发核心概念”包含 Model、Context、Agent Loop、MCP、Harness 等系统课程，不在首次迁移中混入上述主题。它后续可以作为单独的 AI 开发学习路径沉淀。

### 首次拆分结果

现有长文重构为 `content/工具与环境/Codex/` 下的三篇关联文章：

1. `Codex 规则如何生效.md`
   - 主类型：原理与机制。
   - 重点：全局规则、项目规则、目录作用域、覆盖关系和容量边界。

2. `多个项目如何复用 Codex 规则.md`
   - 主类型：操作指南。
   - 重点：全局与项目规则分工、推荐目录、测试策略和跨项目复用方法。

3. `Codex Skill、Plugin、MCP 与 Superpowers.md`
   - 主类型：概念解释与对比。
   - 重点：能力边界、触发与分发方式、组合关系和冲突处理。

三篇必须独立可读，并通过语义链接形成知识网络。如果迁移候选稿需要改变上述路径，必须说明原因并由用户确认。

### 退役顺序

```text
读取原任务和旧文档
→ 展示三篇完整迁移候选稿
→ 用户确认
→ 写入 knowledge-garden/content/
→ 内容校验和 Quartz 构建通过
→ 浏览器检查桌面与窄屏阅读效果
→ 核对知识覆盖和 Git 差异
→ 旧知识目录退役并留下新项目说明
```

任何迁移验证失败都不会触发旧知识目录退役。

## 自动校验

新增 `scripts/validate-content.mjs`，并在 `package.json` 中提供统一入口 `npm run check:content`。脚本复用项目已有 Node.js 运行环境和依赖，不引入新的生产依赖。

所有普通主题文章必须包含合法的 `title`、`description` 和 `tags`；`aliases` 可选，但出现时必须是字符串数组。`content/index.md` 作为首页，只要求合法的 `title`，并允许使用 `cssclasses` 等首页专用字段。实施时只为现有示例文章补齐缺失的必要 frontmatter，不顺带改写其正文。

硬性检查包括：

- frontmatter 可以解析。
- frontmatter 必要字段存在且类型正确。
- 标题、别名和输出路径不存在冲突。
- Markdown 链接和 Wikilink 的本地目标存在。
- 本地图片和附件存在。
- 不存在空标题、空章节或未完成占位标记。
- 首页和主题入口没有失效链接。
- Quartz 可以处理所有新增内容。

Skill 负责无法完全由脚本判断的编辑质量：

- 是否围绕一个学习目标。
- 是否删除对话过程和重复表达。
- 是否选择了合适的文章类型。
- 速览是否准确且足够聚焦。
- 示例、表格和图是否必要。
- 事实、推断和待验证内容是否清楚区分。
- 是否正确复用、拆分或关联已有主题。

## 验证顺序

实施后的最小有效验证顺序为：

1. 运行内容校验脚本。
2. 运行项目 TypeScript 和格式检查。
3. 执行 Quartz 完整构建。
4. 启动本地站点，检查迁移文章的桌面和窄屏阅读效果。
5. 检查搜索、目录、Wikilink、Backlink 和图谱关系。
6. 核对 Git 差异只包含已确认范围。

## 异常处理

- 无法确定素材任务：停止并请求用户指定，不混合多个相似任务。
- 素材不足：候选稿列出缺口，不通过推测填充正文。
- 时效性事实：优先使用官方或一手来源重新核对。
- 新旧知识冲突：候选稿并列展示差异和处理建议。
- 内部链接目标不存在：不创建失效链接，必要时提出新主题建议。
- 构建或内容检查失败：不宣称写入完成，不退役旧知识库。
- 工作区存在无关修改：保留并排除在本次提交之外。
- 校验需要实质改写正文：重新展示完整候选稿并重新确认。

## 首次迁移验收标准

- 原长文拆分为三篇能够独立阅读的主题文章。
- 三篇分别采用机制说明、操作指南和概念对比，不机械共享同一模板。
- 每篇包含聚焦的 `30 秒掌握`，并提供必要的深入内容。
- 原对话中的稳定、可复用知识能够找到明确归属。
- 问答过程、状态汇报、重复解释和临时决策不进入正文。
- 三篇文章之间及与现有主题之间建立有效语义链接。
- 搜索、Wikilink、Backlink 和图谱能够正确识别关系。
- 桌面和窄屏页面均可正常阅读。
- 内容校验、项目检查和 Quartz 完整构建全部通过。
- 迁移验证完成前，旧仓库内容保持不变。

## 风险与回滚

### 风险

- 编辑规则过多导致 Skill 机械化套模板。
- 主题拆分过细导致知识碎片化。
- 标签和链接无约束增长，降低导航质量。
- 校验脚本把合理内容误判为问题。
- 原对话中的时效性产品信息已经变化。
- 退役旧仓库过早导致迁移遗漏难以核对。

### 控制措施

- 文章类型是决策框架，不是固定模板。
- 以独立学习目标和复用价值作为拆分标准。
- 标签使用稳定集合，链接必须表达真实语义关系。
- 硬性校验只处理确定性错误，编辑质量保留人工复核。
- 涉及时效性事实时使用官方来源重新验证。
- 只有所有迁移验收通过后才处理旧知识目录。

### 回滚

- 设计、规则、Skill、校验脚本和迁移文章按目的分开提交。
- 迁移前旧仓库内容保持原状，可用于重新提炼和差异核对。
- Quartz 内容出现问题时可以回滚对应迁移提交，不影响 Quartz 核心代码。
- 默认不推送远端；本地复核完成后再由用户决定是否推送。
